                        Simpler Fields for HTTP
                 draft-toomim-httpbis-simpler-fields-00

Abstract

   Structured Field Values for HTTP (RFC 9651) give HTTP fields a common
   syntax, but a general parser for them is a sizable dependency for a
   light client that needs to read only one or two fields.  This
   document defines Simpler Fields, a profile of Structured Fields that
   a client can parse with a short regular expression.  Its Strings are
   percent-encoded, so they contain no quotes, backslashes, or field
   delimiters.  Its serialization is canonical, and its types are fixed.
   Every Simpler Field value is a valid Structured Field value, so a
   general parser reads it unchanged.

1.  Introduction

   Structured Field Values [RFC9651] define a common syntax for HTTP
   fields: Lists, Dictionaries, and Items, with parameters, built from a
   small set of types.  So a new field needs no grammar of its own, and
   implementations can reuse a well-tested parser to read it.

   However, a general parser is a sizable dependency.  The
   structured-headers package for JavaScript [STRUCTURED-HEADERS], for
   instance, is 10 KB minified.  A light client often needs just one
   field, perhaps in a language without such a library at hand, and
   would rather parse it with a regular expression.  Small parsers like
   that, in many languages, make a protocol easier to implement, and so
   encourage its adoption.

   Strings make Structured Fields hard to parse that way.  A String can
   contain an escaped quote or backslash, and the field's own
   delimiters: commas, semicolons, and parentheses.  So a regular
   expression has to track escapes to find where a String ends.

   This document defines a profile of Structured Fields that removes
   these difficulties.  We call it Simpler Fields.  These are all
   Simpler Fields:


           Version: ("a%2Cb" "c")
           Parents: ("a3" "b7")
           Subscribe: webhook;to="https://gateway.example/push/7f3a"
           Heartbeats: 0.5
           Origin-Status: down;age=12


   In a Simpler Field, a String contains no quotes, backslashes, commas,
   semicolons, or parentheses.  So a regular expression can find every
   String with /"[^"]*"/, and can split the field at its commas and
   semicolons without looking inside its Strings.  The sender
   percent-encodes each String, and the recipient decodes it, so the
   first Event ID above is "a,b".

   Simpler Fields make both kinds of parser possible.  A client can
   parse the one field it needs with a short regular expression of its
   own.  And since every Simpler Field value is also a valid Structured
   Field value, an implementation that handles many fields can use a
   general Structured Fields parser, and add just the decoding step.

   Several fields are Simpler Fields, including Version, Parents, and
   Current-Version [VERSIONS], Subscribe, Heartbeats, and Origin-Status
   [SUBSCRIPTIONS], and Responds-To and Method-Override [MULTIRESPONSE].

2.  Rules for Simpler Fields

   A Simpler Field follows the rules of Structured Fields [RFC9651], and
   also the rules of this section.


2.1.  Strings are percent-encoded

   A sender MUST percent-encode these in a String, as Section 2.1 of
   [RFC3986] describes: every byte of its UTF-8 encoding [RFC3629]
   outside printable ASCII, and the characters DQUOTE, "\", ",", "(",
   ")", ";", and "%".  It MAY percent-encode other characters too.

   After parsing the field, a recipient percent-decodes every String,
   whichever parser it used, since the decoding is part of each field's
   meaning.  A "%" without two hexadecimal digits after it makes the
   field invalid, and so does a decoded value that isn't valid UTF-8.

   Since a percent-encoded String can represent any Unicode character,
   Simpler Fields do not use Display Strings.


2.2.  Serialization is canonical

   A sender MUST serialize each value as Section 4.1 of [RFC9651]
   specifies: with no space after a ";", exactly one space after a ",",
   and exactly one space between the members of an Inner List.  Then
   each Structured Field value has exactly one serialization.

   When a recipient joins field lines, it joins them with a comma and a
   single space, as Section 5.3 of [RFC9110] recommends.  So the joined
   value is canonical too.  A regular expression can match the canonical
   spacing exactly, or be lenient and accept other spacing, such as with
   " ?".


2.3.  The types are fixed

   A Simpler Field uses only these types: Tokens, Strings, Integers,
   Decimals, and Booleans.  It uses Inner Lists only where the field's
   definition calls for them.  It does not use Byte Sequences, Dates, or
   Display Strings.


2.4.  Defining a Simpler Field

   When a specification defines a field as a Simpler Field, it states:

     - its known members and parameters, and their types;

     - the general shape of the members and parameters that it does not
       define, using only the types above, so that a recipient can
       parse them; and

     - what a recipient does with a member or parameter that it does
       not know.

   The last of these matters, because ignoring an unknown parameter can
   be unsafe.  Suppose a member's parameters together identify a
   request.  If a recipient skipped one it didn't know, it would
   identify a different request.  So the definition of such a field
   states that a recipient ignores the whole member.


3.  Parsing a Simpler Field with a regular expression

   When a client reads only a few fields, it can parse each one with a
   short regular expression of its own, written for that field.  When an
   implementation reads many fields, it will do better with a general
   Structured Fields parser, which reads every Simpler Field too.

   Since a String contains no quotes, commas, semicolons, or
   parentheses, a client can safely split a field without Inner Lists at
   its commas, into the members of its List, and split each member at
   its semicolons, into its Item and its parameters.  Then it finds each
   String with /"([^"]*)"/, and percent-decodes it.

   For example, this JavaScript reads the Event IDs from one field line
   of the Version field [VERSIONS]:


           var event_ids = field_line.match(/"[^"]*"/g)
                 .map(s => decodeURIComponent(s.slice(1, -1)))


   And this regular expression reads the Origin-Status field
   [SUBSCRIPTIONS], with its optional age:

           /^(up|down)(?:;age=(\d+))?$/

   A regular expression can still parse a field after the field is
   extended, because the field's definition gives the general shape of
   the parameters it does not define (Section 2.4).  For instance, a
   regular expression can skip unknown parameters with this pattern,
   which matches any key, and any value of the fixed types (Section
   2.3):

           (?:;KEY(?:=(?:VALUE))?)*


   KEY and VALUE stand for these patterns:


           KEY   = [a-z*][a-z0-9_.*-]*
           VALUE = [A-Za-z*][A-Za-z0-9!#$%&'*+.^_`|~:/-]*
                   | "[^"]*" | -?[0-9]+(?:\.[0-9]+)? | \?[01]


4.  Tradeoffs

   A String with special characters is less readable, since it contains
   percent escapes.  Most values, such as typical version identifiers,
   have none.

   Every String takes one decoding step after parsing.

   A general Structured Fields serializer escapes quotes and backslashes
   with a backslash.  So a sender percent-encodes its Strings before
   passing them to such a serializer, which then finds nothing to
   escape.

           Emacs Lisp    59 lines    2.8 KB


6.  Security Considerations

   The security considerations of [RFC9651] apply.

   Percent-decoding can produce any bytes, including control characters.
   A field's definition says which decoded values are valid.  A
   recipient checks each decoded value before using it, as it would any
   String.

   A recipient decodes each String exactly once.  Decoding twice would
   turn "%2541" into "A", so two different Strings would decode to the
   same value, which can defeat a check that compares them.

   Since a sender MAY percent-encode more than it needs to, the same
   value can be serialized as "%41" or as "A".  When a recipient
   compares Strings, as a cache compares versions, it compares their
   decoded values.
