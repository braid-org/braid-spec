                         Subscriptions for HTTP
              draft-toomim-httpbis-braid-subscriptions-01

Abstract

   This document defines the Subscribe header for HTTP requests and
   responses.  A server receiving a request with "Subscribe: stream"
   will respond with the current state, and then leave the response
   open, to stream future updates through, until the subscription ends.
   Each update is itself an HTTP response, which can be cached and
   served by intermediaries.

   Subscriptions can fan out through a tree of intermediaries, so that a
   single origin server connection can serve any number of clients.  At
   each hop in the tree, the connection state can be up or down.  To
   enable any client or intermediary to know the state of its upstream
   connection chain, this document also defines a set of heartbeats and
   origin-status messages, from which a subscription's online/offline
   status can be inferred.

   This document is one of the Braid-HTTP extensions, which add features
   to HTTP, alone or together.  Together, they extend HTTP into a state
   synchronization protocol.

1.  Introduction

   HTTP allows a client to GET the current state of a resource, but does
   not yet provide a way for a client to learn when the resource
   changes.  This sufficed when resources were mostly static, and often
   written by hand, but today's web is increasingly dynamic, and
   applications need to synchronize with resources as they update.

   Applications today have two options.  (1) They can poll the resource
   with repeat GETs at some interval, or (2) they can switch to a
   different protocol, such as WebSocket [RFC6455] or SSE [SSE].
   However, polling is wasteful at short intervals, and incurs delays at
   large intervals.  Alternative protocols lose the advantageous
   semantics of HTTP and REST [REST], such as caching, media types, and
   a uniform interface of method semantics, and incur a second round
   trip from browser to server before a page can load its data.

   This document adds "subscriptions" to HTTP.  A client subscribes to a
   request by adding a "Subscribe" header to it.  The server responds
   immediately with the current state of the resource, along with a
   promise to push additional responses as the resource changes.  Each
   response is sent as if the resource were polled at that moment, and
   is a legitimate HTTP response that can be read, stored, and fanned
   out to clients by caches and intermediaries.

   Section 2 defines subscriptions and specifies their behavior.
   Section 3 specifies how a client or intermediary can know if its
   current subscription is connected and caught up with the origin.

   This document defines the "stream" mode for subscriptions, which
   pushes updates over a long-lived connection.  Servers and paths that
   can't hold a response open can use the long-poll or webhook mode
   [POLL-AND-PUSH].  [SUBSCRIPTIONS-CACHING] specifies how caches store
   and serve subscriptions.

2.  HTTP Subscriptions

   An HTTP subscription is a promise from a server to keep a client
   up to date with responses to a request, as the resource changes
   state, or as the server learns new information about it.

   When a client subscribes to a resource with a GET or a HEAD, the
   server responds in two phases:

      1. Catching the client up

         First, the server responds with information that conveys the
         state of the resource at the time of the request.

      2. Keeping the client caught up

         Then, the server sends additional responses to update the
         client as the resource state changes, or the server learns new
         information, until the subscription ends.

   We call each of these responses within a subscription a
   "sub-response".  For a GET or a HEAD, each of these responses is the
   response that the server would send, at that moment, to the same
   request without its subscription headers (Subscribe, Heartbeats, and
   Origin-Status), and with the sub-response's Parents header.  We call
   that request the sub-response's implied request [MULTIRESPONSE].  A
   cache can store each sub-response as the response to its implied
   request [SUBSCRIPTIONS-CACHING].

   This document defines subscriptions on GET and HEAD.  Future
   specifications can define them for other methods, for instance to
   deliver the result of a POST later, or as the server computes it.  If
   a server doesn't know a meaning for Subscribe on a request's method,
   it ignores the header.


2.1.  The Subscribe Header

   A client requests a subscription by adding a "Subscribe" header to a
   request.  There are three modes of subscription: stream, long-poll,
   and webhook:


      Subscribe: stream

      Subscribe: long-poll

      Subscribe: webhook;to="<url>"


   This document defines the stream mode.  The long-poll and webhook
   modes are defined in [POLL-AND-PUSH].

   The value of the Subscribe header is parsed as a Structured Field
   [RFC9651] List of Tokens, each with optional parameters.  For a
   client to accept multiple modes, it lists them in order of its
   preference, such as:


      Subscribe: stream, long-poll


   The server responds by choosing a mode, and echoing back its choice
   in the response's Subscribe header:


      Response:

         HTTP/1.1 200 OK
         Subscribe: long-poll
         Content-Type: text/plain
         Content-Length: 12

         Hello world!


   The server's response MUST include a Subscribe header if and only if
   it is granting a subscription.  Servers that do not support
   subscriptions MUST NOT respond with a Subscribe header.

   The server SHOULD add "Vary: Subscribe" in response to every
   URI+Method combination that supports subscriptions.


2.2.  The "Subscribe: stream" mode

   In the stream mode, the server sends the whole subscription in one
   multiresponse [MULTIRESPONSE].  For example, a reader's browser
   subscribes to /election:


      Request:

         GET /election
         Subscribe: stream

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK                    | Update
         Version: ("1")                     |
         Content-Type: text/plain           |
         Content-Length: 23                 |
                                            |
         Alice leads, 52% to 48%            |

         HTTP/1.1 200 OK                    | Update
         Version: ("2")                     |
         Parents: ("1")                     |
         Content-Type: text/plain           |
         Content-Length: 21                 |
                                            |
         Bob leads, 51% to 49%              |


   The browser sends one request, and gets two responses: the results
   at version 1, and then, when the results change, version 2.  When a
   client sends "Subscribe: stream", it says that it can read a
   multiresponse, as Section 2.1 of [MULTIRESPONSE] requires.

   The response has the 209 (Multiresponse) status code, the header
   "Subscribe: stream", and the content type application/http-history.
   Like every multiresponse, it has "Cache-Control: no-store".  The
   server keeps the response open, so it SHOULD send "Incremental: ?1"
   [RFC10036], to ask intermediaries to forward each response as it
   arrives.

   The content holds the subscription's responses (Section 2), in order.
   The server SHOULD start the content with a bare CRLF, which every
   recipient skips (Section 3.1 of [MULTIRESPONSE]), since some clients
   and proxies don't deliver a response's header section until its
   content begins.  It SHOULD send each response in one write, so that
   it goes out in as few packets as possible.  If the client asked for
   heartbeats, the server sends each one as a bare CRLF between
   responses (Section 3.2), and it sends 105 (Origin Status)
   sub-responses to say whether the client is caught up (Section 3.3).

   A response to a HEAD has no content, so it can't carry a stream.  To
   subscribe to the header sections in the stream mode, a client sends a
   GET with "Method-Override: HEAD" ([MULTIRESPONSE], Section 5).

   Either side can end the subscription (Section 2.4).  The client ends
   it by resetting its stream in HTTP/2 [RFC9113] or HTTP/3 [RFC9114],
   or by closing its connection in HTTP/1.1.  The server ends it by
   ending the multiresponse.


2.3.  Resuming a subscription with Parents

   When a client knows its current version [VERSIONS], it can resume a
   subscription where it left off, by naming that version in a Parents
   header.  For example, suppose the reader's laptop slept through
   version 3.  When it wakes, it resubscribes:


      Request:

         GET /election
         Subscribe: stream
         Parents: ("2")

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK
         Version: ("3")
         Parents: ("2")
         Content-Type: text/plain
         Content-Length: 20

         Bob wins, 51% to 49%


   The server sends only the change that the laptop missed.  If the
   server doesn't have version "2", it can catch the client up with a
   snapshot of the current state, or respond with a 432 (Version Not
   Found) ([VERSIONS], Section 2.4), as it would to the GET without
   Subscribe.

   A client resumes with Parents, and sends no Version header.  The
   state at a version never changes, so a subscription to it would have
   nothing to send once the client is up to date.  If a subscription
   request has a Version header anyway, the server responds as it would
   to the same GET without Subscribe, and grants no subscription.
   Future specifications can define a subscription at a version, for
   instance to send more of a version's state as the server receives it.


2.4.  Ending a subscription

   A client can end a subscription at any time, as Section 2.2 describes
   for the stream mode.  If it gets more responses than it can handle,
   it can end the subscription, and later resubscribe with Parents, or
   GET the changes since its version whenever it is ready ([VERSIONS],
   Section 2.3.5).

   A server can end a subscription to shed load, or to shut down.  It
   MAY first say why, with a sub-response that has
   "Responds-To: container-request" ([MULTIRESPONSE], Section 4).  For
   example, at the peak of election night, the origin server has more
   subscribers than it can hold, and ends some of their subscriptions
   like this:


         HTTP/1.1 503 Service Unavailable
         Responds-To: container-request
         Retry-After: 30


   Each of those clients resubscribes after 30 seconds, with Parents set
   to its current version, and the server sends it what it missed.  A
   server can refuse a new subscription in the same way, with a 503
   (Service Unavailable) or a 429 (Too Many Requests) response and a
   Retry-After header.

   A subscription can outlast the authorization of its request, as when
   a reader's session expires, or a credential is revoked.  Once the
   request's authorization expires or is revoked, the server MUST NOT
   send more responses, and ends the subscription, as HTTP Events Query
   does for its notifications ([EVENTS-QUERY], Section 5.1).  It MAY
   first send a 403 (Forbidden) sub-response with
   "Responds-To: container-request".


2.5.  Interaction with If-None-Match

   A cache can add an If-None-Match or If-Modified-Since header to a
   request that it forwards, to validate a response that it has stored
   (Section 4.3.1 of [RFC9111]), and a browser's cache can do this to a
   subscription request.  If the server evaluated the header as usual,
   it would respond to a match with a 304 (Not Modified), and the client
   would get no subscription.

   If a server grants a subscription, it MUST ignore the request's
   If-None-Match and If-Modified-Since headers, and respond as if they
   were absent, so that the client gets its subscription.  An extension
   to HTTP can change how a server evaluates preconditions in this way
   (Section 13.2.1 of [RFC9110]).  The cache that added the header gets
   the 209, and passes it on to its client, as it would any full
   response to a validation request (Section 4.3.3 of [RFC9111]).  A
   future specification may give these headers a meaning on a
   subscription.


3.  Origin connection status

   A subscription can reach the origin server through a chain of hops,
   as when a reader subscribes through the paper's CDN, and the CDN
   subscribes to the origin server.  Each client in the chain often
   needs to know whether every hop between it and the origin server is
   connected.  For example, the reader's page can tell the reader
   whether the results are current, and the CDN can decide whether to
   serve its copy without asking the origin server
   [SUBSCRIPTIONS-CACHING].  A client learns whether its own hop is
   connected from heartbeats (Section 3.2), and whether every hop beyond
   it is connected from the origin status that its server sends (Section
   3.3).


3.1.  Catching up, and staying connected

   First, the server brings the client up to date (Section 2).  The
   server can send a Current-Version header ([VERSIONS], Section 2.5) in
   the multiresponse's header section, so that the client can tell when
   it is caught up.

   Then the server sends an origin status of "up" (Section 3.3).  With
   it, the server says that the client is caught up, that every hop
   between the client and the origin server is connected, and that each
   later update will reach the client immediately.  This holds until the
   server sends an origin status of "down", the heartbeats stop, or the
   subscription ends.  After a down, the server sends what the client
   missed, and another up once the client is caught up again.  If no up
   ever comes, the responses still arrive, but the client never learns
   that it is caught up and connected (Section 4).

   A server sends 105 (Origin Status) only on a subscription for which
   it has agreed to send heartbeats (Section 3.2).  Without heartbeats,
   a client can't tell a connection that has died from one that is
   quiet, and could believe that it is connected long after the changes
   stopped coming.


3.2.  Heartbeats

   A server sends heartbeats so that its client can tell that the
   connection is still alive, and so that intermediaries don't close the
   subscription as idle.  For instance, by default, nginx closes its
   connection to a proxied server that has sent nothing for 60 seconds
   [NGINX].

   A client asks for heartbeats with the Heartbeats header, giving the
   interval that it wants, in seconds:


         Heartbeats: 20


   Heartbeats is a Structured Field Item [RFC9651].  Its value is a
   number of seconds, as a Decimal or an Integer, such as 20, or 0.5
   within a data center.  In its response, the server gives the interval
   that it will use, which can be longer than the one the client asked
   for.  If the response has no Heartbeats header, the server sends no
   heartbeats.

   In the stream mode, each heartbeat is a bare CRLF between two
   responses, which every recipient skips (Section 3.1 of
   [MULTIRESPONSE]).  The server sends at least one heartbeat or
   response in each interval.  The server sends each heartbeat on the
   subscription's own stream, so when a heartbeat arrives, the client
   also knows that the server is still sending this subscription.  From
   an HTTP/2 PING frame, a client learns only that the connection is
   alive, and an application can't see the frame through fetch()
   [FETCH].

   Each hop has its own heartbeats.  Each server, whether the origin
   server or a cache, sends heartbeats to its own client, at the
   interval that client agreed to, and a cache picks its own interval
   for its own subscription upstream.  If a proxy relays the
   multiresponse byte for byte, it forwards the heartbeats with the
   rest.

   A client waits a little longer than the interval, to allow for
   network delay: for instance, 1.2 times the interval, plus 3 seconds.
   If neither a heartbeat nor a response arrives in that time, the
   client treats the connection as dead, and the subscription as ended.
   If the client is a cache, it sends an origin status of "down" to its
   own subscribers.  Then the client
   resubscribes, with Parents set to its current version.


3.3.  Status 105 and the Origin-Status Header

   A server sends a 105 (Origin Status) sub-response to tell its client
   whether the client is caught up, and whether every hop between the
   client and the origin server is connected.  For example, a reader
   subscribes through the paper's CDN, which catches the reader up, and
   then says so:


      Request:

         GET /election
         Subscribe: stream
         Heartbeats: 20

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Heartbeats: 20
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK
         Version: ("2")
         Content-Type: text/plain
         Content-Length: 21

         Bob leads, 51% to 49%

         HTTP/1.1 105 Origin Status
         Responds-To: container-request
         Origin-Status: up
         Current-Version: ("2")
         Date: Wed, 04 Nov 2026 03:00:00 GMT


   Later, the CDN stops hearing from the origin server.  When its own
   subscription times out, 30 seconds after the last heartbeat it heard,
   it tells the reader:


         HTTP/1.1 105 Origin Status
         Responds-To: container-request
         Origin-Status: down;age=30
         Proxy-Status: ExampleCDN; error=connection_read_timeout
         Date: Wed, 04 Nov 2026 03:20:30 GMT


   Origin-Status is a Structured Field Item [RFC9651], whose value is a
   Token: "up" or "down".  A recipient treats any other value as "down".
   A 105 has no content.  It has "Responds-To: container-request"
   ([MULTIRESPONSE], Section 4), since it responds to the subscription
   request itself.  Its Date header says when the server sent it.  An up
   can have a Current-Version header [VERSIONS], naming the version that
   the client is now caught up to.  A down can have a Proxy-Status
   header [RFC9209], saying which hop lost its connection, and why.

   A down can have an "age" parameter, an Integer number of seconds
   since every hop was last known to be connected.  When a cache sends a
   down because it received one, the cache adds the time it held the
   down to the age it received, as caches compute the Age header
   (Section 5.1 of [RFC9111]), so that hops whose clocks disagree still
   agree on the age.  The age is a parameter, since the Age header
   already gives a response's own age.

   Each server sends its own 105s, with the status of the whole chain of
   hops from that server to the origin server:

     - The origin server sends an up as soon as the client is caught up.

     - A cache sends an up to a client once that client holds the
       cache's current version, and the cache's own upstream
       subscription is up: the cache has received an up on it, and no
       down since, and its heartbeats still arrive.  It sends a down to
       each client as soon as that stops being true: when it receives a
       down, when its heartbeats stop, or when its upstream subscription
       ends.

     - If a proxy relays the multiresponse byte for byte, it passes the
       105s on with the rest.

   When a cache builds its own multiresponse, it doesn't forward the
   105s it receives, since they respond to its own request
   ([MULTIRESPONSE], Section 2.4).  A server sends 105s only on a
   subscription with heartbeats (Section 3.1).

   A 1xx status code suits origin status.  RFC 9110 defines the 1xx
   class for communicating "connection status or request progress"
   (Section 15.2 of [RFC9110]).  A 1xx response has no content, and a
   recipient ignores a 1xx sub-response that it doesn't know
   ([MULTIRESPONSE], Section 2.3).  This document defines 105 only as a
   sub-response.  If a client receives a 105 as an interim response, it
   ignores the 105, as it can any 1xx that it doesn't expect.  A future
   specification may give it a meaning there.


4.  Interaction with legacy intermediaries

   The client, the origin server, and any intermediaries between them
   may each predate this document.  Each one either understands
   subscriptions, or falls back to what HTTP already does:

     - If a server doesn't know the Subscribe header, it sends the
       response that the GET would get without it, with no Subscribe
       header, so the client knows that it isn't subscribed.

     - If a client doesn't know the 105 status code, it ignores 105
       sub-responses, as it does any 1xx sub-response that it doesn't
       know ([MULTIRESPONSE], Section 2.3).

     - If a proxy relays the multiresponse byte for byte, it passes on
       the heartbeats and 105s with the rest, so its client still gets
       the origin status.  When its connection upstream breaks, it ends
       the response, and when the connection stalls, the heartbeats
       stop.  Either way, its client learns that the connection is
       lost.

     - If a cache doesn't know subscriptions, it still honors
       "Vary: Subscribe" (Section 2.1), so it doesn't respond to a
       subscription request with a response it stored for an ordinary
       GET.  The 209 has "Cache-Control: no-store", so the cache doesn't
       store it, and can't replay the subscription later, old ups and
       all.  The server also ignores any If-None-Match or
       If-Modified-Since header that the cache adds to a subscription
       request (Section 2.5).

     - If a cache builds its own multiresponse but doesn't know origin
       status, it doesn't forward the 105s it receives ([MULTIRESPONSE],
       Section 2.4), so it passes on no up.  Its clients still get every
       change, but never learn that they are caught up and connected.

     - If an origin server sends no up, its clients still receive each
       update, and caches can still serve one subscription to many
       clients, but no client ever receives an up.  The site that runs
       the origin server can tell its CDN, by configuration, that the
       origin server sends each update immediately.  Then the CDN sends
       origin status itself: an up while its connection to the origin
       server holds, and a down when that connection is lost.


5.  Implementation Status

   This section records the known implementations of this document, as
   [RFC7942] describes.  It is to be removed before publishing as an
   RFC.

     - The reference JavaScript library [BRAID-HTTP-JS], for clients and
       servers, sends and parses subscriptions in the stream mode, with
       heartbeats, the first CRLF, and 105 (Origin Status).  Its client
       resumes a subscription with Parents when the connection drops, or
       when the heartbeats stop for 1.2 times the interval plus 3
       seconds.

     - braid-text [BRAID-TEXT], a library for synchronizing text, serves
       subscriptions to text resources, resumes them from Parents, sends
       Current-Version, and accepts "Method-Override: HEAD".

     - The Braid-HTTP polyfill for Cloudflare [CDN-POLYFILLS] holds one
       subscription to the origin server for each resource, and serves
       it to every reader at each of Cloudflare's data centers.  It
       sends its own 105s, with Current-Version on an up, and can be
       configured to send ups for an origin server that sends none.
       With it, an origin server updates the cache at the edge in half a
       round trip, where a purge and a refetch take one and a half
       [MEETING-144].

     - braid-chrome [BRAID-CHROME], a browser extension for Chrome and
       Firefox, and editor plugins for Emacs [BRAID-EMACS], Neovim
       [BRAID-NEOVIM], and VS Code [BRAID-VSCODE] subscribe to
       resources, to show and edit them as they change.

   In September 2026 we tested subscriptions through Cloudflare's
   network, with tests that we wrote for the HTTP cache-tests engine
   [CACHE-TESTS].  Cloudflare passed each 209 through, streaming each
   response as the server sent it.


6.  Security Considerations

   A server holds a connection, and memory, for each subscription, for
   as long as the subscription lasts.  To bound these costs, a server
   can limit how many subscriptions it holds for each client, end any
   subscription at any time (Section 2.4), refuse new ones with a 503
   (Service Unavailable) or 429 (Too Many Requests) response, and
   respond to a request for heartbeats with a longer interval than the
   client asked for (Section 3.2).  If a cache serves one subscription
   to many clients, the origin server holds just that one
   [SUBSCRIPTIONS-CACHING].

   A server keeps sending a subscription's responses long after it
   authorized the request, so it MUST NOT send more once the request's
   authorization expires or is revoked (Section 2.4).

   Each response responds to an implied request with the same target URI
   and credentials as the client's own request ([MULTIRESPONSE], Section
   2.2), so a server sends a subscriber only what the subscriber's own
   GET could get.

   A client trusts the origin status that its server sends, as it trusts
   that server's responses.  With a Proxy-Status header on a down, a
   server can reveal the hops inside its operator's network, and the
   errors between them.  The security considerations of [RFC9209]
   apply, and an operator can leave the header out.
