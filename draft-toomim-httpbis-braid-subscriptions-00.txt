                         Subscriptions for HTTP
              draft-toomim-httpbis-braid-subscriptions-00

Abstract

   Servers respond to an HTTP GET with a resource's current state.
   However, if the resource changes afterward, HTTP has no way for the
   server to notify its client of the new version.  This document
   defines subscriptions.  When a client adds the Subscribe header to a
   GET, the server responds with the resource's current state, and then
   continues to respond as subsequent changes occur.  Each response
   corresponds to a semantically-equivalent GET, so that content
   negotiation, authorization, and caching work as they do for any GET
   request.

   When a server grants a subscription, it promises to send each change
   as it happens.  So once a client is caught up, and while its
   connection is alive, it knows that nothing has changed until the next
   response arrives.  The server tells the client when the client has
   caught up with the origin server's current version, and sends
   heartbeats to show that the connection is alive.  If a cache holds
   such a subscription, it knows at every moment that its stored copy is
   current, and can respond to requests with the copy, without asking
   the origin server.

   This document is one of the Braid-HTTP extensions, which work alone
   or together; together they make HTTP a state synchronization
   protocol.

1.  Introduction

   A server responds to an ordinary GET once.  If the resource changes
   afterward, the client does not hear about it, unless it asks again.
   For example, imagine a newspaper's website on election night, with a
   results page at /election that changes all evening.  Every reader
   reloads the results page, again and again.  A cache can respond to
   the reloads with its stored copy only while the copy is fresh, so the
   site has to choose between stale results and a flood of requests to
   its origin server.  Sites that want their pages to change with the
   news often send each change over a WebSocket [RFC6455], which
   bypasses the caches entirely.  The examples in this document follow
   this site through the night.


   With a subscription, a reader's browser sends its GET once, with a
   Subscribe header, and the server keeps responding:


      Request:

         GET /election
         Subscribe: stream

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK                    | The results at version 1
         Version: ("1")                     |
         Content-Type: text/plain           |
         Content-Length: 23                 |
                                            |
         Alice leads, 52% to 48%            |

         HTTP/1.1 200 OK                    | The change to version 2,
         Version: ("2")                     | as it happens
         Parents: ("1")                     |
         Content-Type: text/plain           |
         Content-Length: 21                 |
                                            |
         Bob leads, 51% to 49%              |


   The browser sends one request, and gets two responses here.  The
   first holds the results at version 1, and the second arrives when the
   results change to version 2.  Each one is an ordinary HTTP response.
   The server sends them inside one 209 (Multiresponse) response
   [MULTIRESPONSE], and with an Incremental header [RFC10036], it asks
   intermediaries to forward each one as soon as it is sent.  With the
   Version and Parents headers [VERSIONS], it says which point in time
   each one is at.

   A cache can subscribe, too.  It holds one subscription to the origin
   server, and serves it to every reader who asks the cache for one
   [SUBSCRIPTIONS-CACHING].  Each time the results change, the origin
   server updates the cache in half a round trip.  The cache can then
   respond even to plain GETs with the new results, without asking the
   origin server.  And if an origin server can't hold a response open,
   as on serverless hosting, it can still deliver each change to its
   readers as it happens [POLL-AND-PUSH].


   This document defines how a client asks for a subscription, with the
   Subscribe header (Section 3), and how a server sends the whole
   subscription in one multiresponse, in the stream mode (Section 4).
   It also defines how a server tells its client whether the client's
   copy of the resource is validated, with the Heartbeats header and the
   105 (Origin Status) status code (Section 5).

   Of the other Braid-HTTP extensions [BRAID-HTTP], subscriptions need
   only Multiresponse, which the stream mode uses.  With Versions
   [VERSIONS], a client can resume a subscription where it left off.
   With Updates [UPDATES], the server can send each change as a patch,
   and every peer that replays the patches reaches the same state.


1.1.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   This document uses these terms from Multiresponse [MULTIRESPONSE]:
   multiresponse, sub-response, container request, and implied request.
   It uses these from Versions [VERSIONS]: Version, Parents, and current
   version.  Its new fields are Simpler Fields [SIMPLER-FIELDS].  It
   also uses these terms:

   Subscription:  A GET request that the server keeps responding to,
      with a new response each time the resource changes.

   Catch-up:  The responses that bring a client up to the server's
      current version, as at the start of a subscription (Section 2).

   Caught up:  Holding the origin server's current version.

   Hop:  One connection on the path between a client and the origin
      server, as from a client to a cache, or from a cache to the origin
      server.

   Origin status:  Whether a client is caught up, with every hop between
      it and the origin server connected (Section 5.2).

   Validated:  Known to match the resource's current state at the origin
      server, as a stored copy is when a validation request (Section 4.3
      of [RFC9111]) would bring back nothing new.

   Continuously validating:  The state of a subscription between an
      origin status of "up" and the next "down", while its heartbeats
      arrive.  The client's copy is validated at every moment of this
      time (Section 5).


2.  Subscription messages are responses to implied requests

   Each response in a subscription is one that the client could have
   gotten on its own, by sending the same GET at another time.  It is
   the response that the server would have sent to the same GET, without
   the Subscribe and Heartbeats headers, just after the change that the
   response describes.  When the client knows its current version
   ([VERSIONS], Section 2.2.3), that GET has a Parents header naming the
   version that the client held just before the change.

   These GETs are the subscription's implied requests [MULTIRESPONSE].
   In the example in Section 1, the first response responds to an
   ordinary GET, which any reader could send:


         GET /election


   And the second responds to the GET that a client holding version "1"
   would have sent, just after the change to version 2:


         GET /election
         Parents: ("1")


   The first responses bring the client up to the server's current
   version, and we call them the "catch-up".  A new subscriber's
   catch-up is often one snapshot of the current state.  When a client
   resumes a subscription from a version (Section 3.1), its catch-up
   holds only the changes since that version.  If the client already
   holds the current version, its catch-up is empty, since nothing has
   changed.

   So the server sends the subscriber a history of ordinary HTTP
   responses, which every HTTP peer already understands.  Everything
   that HTTP defines for a GET applies to each one.  The server selects
   each subscriber's variant by content negotiation.  For instance, a
   reader who sends "Accept-Language: es" gets each change in Spanish.
   The Vary header applies too.  The server authorizes each implied
   request with the subscriber's own credentials, as it would the
   subscriber's GET.  And a cache can store each response as the
   response to its implied request, as [SUBSCRIPTIONS-CACHING]
   describes.

   The responses can be any responses.  For example, a reader who
   subscribes to /election before the polls close gets a 404 (Not Found)
   as the catch-up, and then the first results, as soon as they are
   posted.  When the responses are updates [UPDATES], every peer that
   replays them reaches the same state.


   When a server grants a subscription, it promises to keep the client
   caught up, and no more.  Clients and servers negotiate the rest with
   other mechanisms: how often responses come, how they are rebased, and
   which merge types, patch formats, and version types they use, as the
   Merge-Type [MERGE-TYPES] and Accept-Patch [UPDATES] headers do.
   There are many ways to view the same history, and subscriptions work
   with any of them.


3.  The Subscribe Header

   A client asks for a subscription by sending a GET with a Subscribe
   header.  Its value lists the subscription modes that the client
   accepts, in order of preference:


         Subscribe: stream


   This document defines the "stream" mode (Section 4).  If a client
   also accepts long polling [POLL-AND-PUSH], it lists both:
   "Subscribe: stream, long-poll".  Subscribe is a Simpler Field
   [SIMPLER-FIELDS].  Its value is a List of Tokens, each naming a mode.
   A mode can have parameters.  A server ignores any mode that it
   doesn't know.

   If the server grants a subscription, its response has a Subscribe
   header naming the mode it granted, with that mode's parameters.  If
   the response has no Subscribe header, the server did not grant one,
   perhaps because it doesn't know the header.  The response is then the
   one that the GET would get without Subscribe, and the client can
   poll, or try again later.

   A server SHOULD send "Vary: Subscribe" in every response to a GET for
   a resource that a client can subscribe to.  Then if a cache doesn't
   know subscriptions, it won't respond to a subscription request with a
   response that it stored for an ordinary GET (Section 7).  And a
   client can take the Vary header as a sign that it can subscribe to
   the resource.

   This document defines Subscribe on GET.  Future specifications can
   define its meaning on other methods, for instance to deliver the
   result of a POST later, or as the server computes it.  If a server
   doesn't know a meaning for Subscribe on a request's method, it
   ignores the header.


3.1.  Resuming a subscription with Parents

   When a client knows its current version [VERSIONS], it can resume a
   subscription where it left off, by naming that version in a Parents
   header.  For example, suppose the reader's laptop slept through
   version 3.  When it wakes, it resubscribes:


      Request:

         GET /election
         Subscribe: stream
         Parents: ("2")

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK
         Version: ("3")
         Parents: ("2")
         Content-Type: text/plain
         Content-Length: 20

         Bob wins, 51% to 49%


   The catch-up holds only the change that the laptop missed.  If the
   server doesn't have version "2", it can catch the client up with a
   snapshot of the current state, or respond with a 432 (Version Not
   Found) ([VERSIONS], Section 2.4), as it would to the GET without
   Subscribe.

   A client resumes with Parents, and sends no Version header.  The
   state at a version never changes, so a subscription to it would have
   nothing to send after its catch-up.  If a subscription request has a
   Version header anyway, the server responds as it would to the same
   GET without Subscribe, and grants no subscription.  Future
   specifications can define a subscription at a version, for instance
   to send more of a version's state as the server receives it.


3.2.  Subscribing to headers only, with Method-Override

   Some subscribers need to know only when the resource changes, and to
   which version.  For example, the paper's notification server alerts
   its readers' phones whenever the results change, and has no use for
   the results themselves.  So it subscribes with
   "Method-Override: HEAD" ([MULTIRESPONSE], Section 5):


      Request:

         GET /election
         Subscribe: stream
         Method-Override: HEAD

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1
         Method-Override: HEAD

         HTTP/1.1 200 OK
         Version: ("1")
         Content-Type: text/plain
         Content-Length: 23

         HTTP/1.1 200 OK
         Version: ("2")
         Parents: ("1")
         Content-Type: text/plain
         Content-Length: 21


   Each implied request is then a HEAD, so each response has the header
   section that the GET's response would have, and no content.  A client
   can use such a subscription as an index of the resource's history,
   and GET the versions it needs.


3.3.  Servers ignore If-None-Match on subscriptions

   A cache can add an If-None-Match or If-Modified-Since header to a
   request that it forwards, to validate a response that it has stored
   (Section 4.3.1 of [RFC9111]), and a browser's cache can do this to a
   subscription request.  If the server evaluated the header as usual,
   it would respond to a match with a 304 (Not Modified), and the client
   would get no subscription.


   So if a server grants a subscription, it MUST ignore the request's
   If-None-Match and If-Modified-Since headers, and send the catch-up as
   if they were absent.  An extension to HTTP can change how a server
   evaluates preconditions in this way (Section 13.2.1 of [RFC9110]).
   The cache that added the header gets the 209, and passes it on to its
   client, as it would any full response to a validation request
   (Section 4.3.3 of [RFC9111]).  A future specification may give these
   headers a meaning on a subscription.


4.  The "Subscribe: stream" mode creates a 209 Multiresponse

   In the stream mode, the server sends the whole subscription in one
   multiresponse [MULTIRESPONSE], as in the example in Section 1.  When
   a client sends "Subscribe: stream", it says that it can read a
   multiresponse, as Section 2.1 of [MULTIRESPONSE] requires.

   The response has the 209 (Multiresponse) status code, the header
   "Subscribe: stream", and the content type application/http-history.
   Like every multiresponse, it has "Cache-Control: no-store".  The
   server keeps the response open, so it SHOULD send "Incremental: ?1"
   [RFC10036], to ask intermediaries to forward each response as it
   arrives.

   The content holds the catch-up, and then a response for each change,
   as it happens.  The server SHOULD start the content with a bare CRLF,
   which every recipient skips (Section 3.1 of [MULTIRESPONSE]), since
   some clients and proxies don't deliver a response's header section
   until its content begins.  It SHOULD send each response in one write,
   so that it goes out in as few packets as possible.  If the client
   asked for heartbeats, the server sends each one as a bare CRLF
   between responses (Section 5.1), and it sends 105 (Origin Status)
   sub-responses to say whether the client is caught up (Section 5.2).

   Either side can end the subscription (Section 6).  The client ends it
   by resetting its stream in HTTP/2 [RFC9113] or HTTP/3 [RFC9114], or
   by closing its connection in HTTP/1.1.  The server ends it by ending
   the multiresponse.

   Poll and Push [POLL-AND-PUSH] defines two more modes: "long-poll", in
   which the client sends a GET for each response, and "webhook", in
   which the origin server pushes each change to another server, as a
   PUT or a DELETE.


5.  Subscriptions create continuous cache validation

   Consider the paper's CDN, which stores /election, and responds to
   readers' reloads with its copy.  Ordinarily, it validates its copy
   from time to time, by asking the origin server whether the copy is
   still current (Section 4.3 of [RFC9111]).  With a subscription, it
   can stop asking.  The origin server has promised to send each change
   as it happens.  So once the CDN is caught up, and while its
   connection is alive, it knows that its copy is current until the next
   response arrives.  A validation request would bring back nothing new,
   so the CDN's copy is validated at every moment.  A subscription is a
   validation that keeps going.

   A subscription's timeline runs like this:


         catch-up                          unvalidated
         105, Origin-Status: up       --+
         each change, as it happens     |  continuously
         heartbeats                     |  validating
         105, Origin-Status: down     --+
         catch-up                          unvalidated
         105, Origin-Status: up       --+
         ...                            |


   The catch-up comes first, and brings the client up to the server's
   current version.  The server can send a Current-Version header
   ([VERSIONS], Section 2.5) in the multiresponse's header section, so
   that the client can tell when the catch-up is complete.

   Then the server sends an origin status of "up" (Section 5.2).  With
   it, the server says that the client is caught up, that every hop
   between the client and the origin server is connected, and that each
   later change will arrive as it happens.  From that moment until the
   server sends an origin status of "down", or the subscription ends,
   the subscription is continuously validating.  The client's copy is
   validated at every moment, and so is each response that arrives.
   After a down, the server fills in what the client missed with a new
   catch-up, and sends another up once the client is caught up again.

   Validation starts exactly at the up, and covers the state that the
   catch-up left the client in.  No response in a catch-up is validated
   as it arrives.  If no up ever comes, the responses still arrive, but
   nothing is validated (Section 7).

   Validation also needs heartbeats.  Without them, a client can't tell
   a connection that has died from one that is quiet, and could take its
   copy for validated long after the changes stopped coming.  So a
   server sends 105 (Origin Status) only on a subscription for which it
   has agreed to send heartbeats (Section 5.1).

   A cache can use a validated copy to satisfy ordinary GETs and
   conditional requests, without asking the origin server, as
   [SUBSCRIPTIONS-CACHING] describes.


5.1.  The Heartbeats Header

   A server sends heartbeats so that its client can tell that the
   connection is still alive, and so that intermediaries don't close the
   subscription as idle.  For instance, by default, nginx closes its
   connection to a proxied server that has sent nothing for 60 seconds
   [NGINX].

   A client asks for heartbeats with the Heartbeats header, giving the
   interval that it wants, in seconds:


         Heartbeats: 20


   Heartbeats is a Simpler Field [SIMPLER-FIELDS].  Its value is a
   number of seconds, as a Decimal or an Integer, such as 20, or 0.5
   within a data center.  In its response, the server gives the interval
   that it will use, which can be longer than the one the client asked
   for.  If the response has no Heartbeats header, the server sends no
   heartbeats.

   In the stream mode, each heartbeat is a bare CRLF between two
   responses, which every recipient skips (Section 3.1 of
   [MULTIRESPONSE]).  The server sends at least one heartbeat or
   response in each interval.  The server sends each heartbeat on the
   subscription's own stream, so when a heartbeat arrives, the client
   also knows that the server is still sending this subscription.  From
   an HTTP/2 PING frame, a client learns only that the connection is
   alive, and an application can't see the frame through fetch()
   [FETCH].

   Each hop has its own heartbeats.  Each server, whether the origin
   server or a cache, sends heartbeats to its own client, at the
   interval that client agreed to, and a cache picks its own interval
   for its own subscription upstream.  If a proxy relays the
   multiresponse byte for byte, it forwards the heartbeats with the
   rest.

   A client waits a little longer than the interval, to allow for
   network delay: for instance, 1.2 times the interval, plus 3 seconds.
   If neither a heartbeat nor a response arrives in that time, the
   client treats the connection as dead, and the subscription as ended.
   Validation stops then.  If the client is a cache, it sends an origin
   status of "down" to its own subscribers.  Then the client
   resubscribes, with Parents set to its current version.


5.2.  Status 105 and the Origin-Status Header

   A server sends a 105 (Origin Status) sub-response to tell its client
   whether the client is caught up, and whether every hop between the
   client and the origin server is connected.  For example, a reader
   subscribes through the paper's CDN, which catches the reader up, and
   then says so:


      Request:

         GET /election
         Subscribe: stream
         Heartbeats: 20

      Response:

         HTTP/1.1 209 Multiresponse
         Subscribe: stream
         Heartbeats: 20
         Content-Type: application/http-history
         Cache-Control: no-store
         Incremental: ?1

         HTTP/1.1 200 OK
         Version: ("2")
         Content-Type: text/plain
         Content-Length: 21

         Bob leads, 51% to 49%

         HTTP/1.1 105 Origin Status
         Responds-To: container-request
         Origin-Status: up
         Current-Version: ("2")
         Date: Wed, 04 Nov 2026 03:00:00 GMT


   Later, the CDN stops hearing from the origin server.  When its own
   subscription times out, 30 seconds after the last heartbeat it heard,
   it tells the reader:


         HTTP/1.1 105 Origin Status
         Responds-To: container-request
         Origin-Status: down;age=30
         Proxy-Status: ExampleCDN; error=connection_read_timeout
         Date: Wed, 04 Nov 2026 03:20:30 GMT


   Origin-Status is a Simpler Field [SIMPLER-FIELDS], whose value is a
   Token: "up" or "down".  A recipient treats any other value as "down".
   A 105 has no content.  It has "Responds-To: container-request"
   ([MULTIRESPONSE], Section 4), since it responds to the subscription
   request itself.  Its Date header says when the server sent it.  An up
   can have a Current-Version header [VERSIONS], naming the version that
   the client is now caught up to.  A down can have a Proxy-Status
   header [RFC9209], saying which hop lost its connection, and why.

   A down can have an "age" parameter, an Integer number of seconds
   since every hop was last known to be connected.  When a cache sends a
   down because it received one, the cache adds the time it held the
   down to the age it received, as caches compute the Age header
   (Section 5.1 of [RFC9111]).  So hops whose clocks disagree still
   agree on the age.  The age is a parameter, since the Age header
   already gives a response's own age.

   Each server sends its own 105s, with the status of the whole chain of
   hops from that server to the origin server:

     - The origin server sends an up as soon as the client is caught up.

     - A cache sends an up to a client once that client holds the
       cache's current version, and the cache's own subscription
       upstream is continuously validating.  It sends a down to each
       client as soon as its own subscription stops validating: when it
       receives a down, when its heartbeats stop, or when it ends.

     - If a proxy relays the multiresponse byte for byte, it passes the
       105s on with the rest.

   When a cache builds its own multiresponse, it doesn't forward the
   105s it receives, since they respond to its own request
   ([MULTIRESPONSE], Section 2.4).  A server sends 105s only on a
   subscription with heartbeats (Section 5).

   A 1xx status code suits origin status.  RFC 9110 defines the 1xx
   class for communicating "connection status or request progress"
   (Section 15.2 of [RFC9110]).  A 1xx response has no content, and a
   recipient ignores a 1xx sub-response that it doesn't know
   ([MULTIRESPONSE], Section 2.3).  This document defines 105 only as a
   sub-response.  If a client receives a 105 as an interim response, it
   ignores the 105, as it can any 1xx that it doesn't expect.  A future
   specification may give it a meaning there.


6.  Subscriptions can be ended by client or server

   A client can end a subscription at any time, as Section 4 describes
   for the stream mode.  If it gets more responses than it can handle,
   it can end the subscription, and later resubscribe with Parents, or
   GET the changes since its version whenever it is ready ([VERSIONS],
   Section 2.3.5).

   A server can end a subscription to shed load, or to shut down.  It
   MAY first say why, with a sub-response that has
   "Responds-To: container-request" ([MULTIRESPONSE], Section 4).  For
   example, at the peak of election night, the origin server has more
   subscribers than it can hold, and ends some of their subscriptions
   like this:


         HTTP/1.1 503 Service Unavailable
         Responds-To: container-request
         Retry-After: 30


   Each of those clients resubscribes after 30 seconds, with Parents set
   to its current version, and its catch-up brings it what it missed.  A
   server can refuse a new subscription in the same way, with a 503
   (Service Unavailable) or a 429 (Too Many Requests) response and a
   Retry-After header.

   A subscription can outlast the authorization of its request, as when
   a reader's session expires, or a credential is revoked.  Once the
   request's authorization expires or is revoked, the server MUST NOT
   send more responses, and ends the subscription, as HTTP Events Query
   does for its notifications ([EVENTS-QUERY], Section 5.1).  It MAY
   first send a 403 (Forbidden) sub-response with
   "Responds-To: container-request".


7.  Subscriptions can function with legacy intermediaries

   The client, the origin server, and any intermediaries between them
   may each predate this document.  Each one either understands
   subscriptions, or falls back to what HTTP already does:

     - If a server doesn't know the Subscribe header, it sends the
       response that the GET would get without it, with no Subscribe
       header, so the client knows that it isn't subscribed.

     - If a client doesn't know the 105 status code, it ignores 105
       sub-responses, as it does any 1xx sub-response that it doesn't
       know ([MULTIRESPONSE], Section 2.3).

     - If a proxy relays the multiresponse byte for byte, it passes on
       the heartbeats and 105s with the rest, so its client still gets
       the origin status.  When its connection upstream breaks, it ends
       the response, and when the connection stalls, the heartbeats
       stop.  Either way, its client stops validating.

     - If a cache doesn't know subscriptions, it still honors
       "Vary: Subscribe" (Section 3), so it doesn't respond to a
       subscription request with a response it stored for an ordinary
       GET.  The 209 has "Cache-Control: no-store", so the cache doesn't
       store it, and can't replay the subscription later, old ups and
       all.  And the server ignores any If-None-Match or
       If-Modified-Since header that the cache adds to a subscription
       request (Section 3.3).

     - If a cache builds its own multiresponse but doesn't know origin
       status, it doesn't forward the 105s it receives ([MULTIRESPONSE],
       Section 2.4), so it passes on no up, and its clients' copies are
       not validated.  That is safe, since its clients still get every
       change.

     - If an origin server sends no up, its responses still arrive as
       each change happens, and caches can still serve one subscription
       to many clients, but nothing is validated.  But the site that
       runs the origin server can tell its CDN, by configuration, that
       the origin server sends each change as it happens.  Then the CDN
       sends origin status itself: an up while its connection to the
       origin server holds, and a down when that connection is lost.
       The CDN then sends a down when it loses its connection to the
       origin server.


8.  Implementation Status

   This section records the known implementations of this document, as
   [RFC7942] describes.  It is to be removed before publishing as an
   RFC.

     - The reference JavaScript library [BRAID-HTTP-JS], for clients and
       servers, sends and parses subscriptions in the stream mode, with
       heartbeats, the first CRLF, and 105 (Origin Status).  Its client
       resumes a subscription with Parents when the connection drops, or
       when the heartbeats stop for 1.2 times the interval plus 3
       seconds.

     - braid-text [BRAID-TEXT], a library for synchronizing text, serves
       subscriptions to text resources, resumes them from Parents, sends
       Current-Version, and accepts "Method-Override: HEAD".

     - The Braid-HTTP polyfill for Cloudflare [CDN-POLYFILLS] holds one
       subscription to the origin server for each resource, and serves
       it to every reader at each of Cloudflare's data centers.  It
       sends its own 105s, with Current-Version on an up, and can be
       configured to send ups for an origin server that sends none.
       With it, an origin server updates the cache at the edge in half a
       round trip, where a purge and a refetch take one and a half
       [MEETING-144].

     - braid-chrome [BRAID-CHROME], a browser extension for Chrome and
       Firefox, and editor plugins for Emacs [BRAID-EMACS], Neovim
       [BRAID-NEOVIM], and VS Code [BRAID-VSCODE] subscribe to
       resources, to show and edit them as they change.

   In September 2026 we tested subscriptions through Cloudflare's
   network, with tests that we wrote for the HTTP cache-tests engine
   [CACHE-TESTS].  Cloudflare passed each 209 through, streaming each
   response as the server sent it.


9.  Security Considerations

   A server holds a connection, and memory, for each subscription, for
   as long as the subscription lasts.  So a server can limit how many
   subscriptions it holds for each client, end any subscription at any
   time (Section 6), refuse new ones with a 503 (Service Unavailable) or
   429 (Too Many Requests) response, and respond to a request for
   heartbeats with a longer interval than the client asked for (Section
   5.1).  If a cache serves one subscription to many clients, the origin
   server holds just that one [SUBSCRIPTIONS-CACHING].

   A server keeps sending a subscription's responses long after it
   authorized the request.  So the server MUST NOT send more responses
   once the request's authorization expires or is revoked (Section 6).

   Each response responds to an implied request with the same target URI
   and credentials as the client's own request ([MULTIRESPONSE], Section
   2.2), so a server sends a subscriber only what the subscriber's own
   GET could get.

   A client trusts the origin status that its server sends, as it trusts
   that server's responses.  With a Proxy-Status header on a down, a
   server can reveal the hops inside its operator's network, and the
   errors between them.  So the security considerations of [RFC9209]
   apply, and an operator can leave the header out.
